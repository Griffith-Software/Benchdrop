# Benchdrop

A warm-toned workshop for running whatever you drop on the bench.

A tiny Windows desktop app: drop in a zipped web-app project, it installs the
dependencies and runs it inside its own window. No Node.js/npm install
required on the target computer — Benchdrop uses one if you have it, and otherwise
downloads its own copy automatically.

**Requirements:** Windows 10 (22H2) or Windows 11, 64-bit (x64). Nothing else
to install.

## What you can drop in

* a **.zip** of a project
* a **folder** — used where it sits, so edits in your own editor show on reload
* a single **.html** page — served on its own, useful for standalone apps
* a single **.py** script
* a **.md** file — rendered as a readable page rather than shown as raw text

## Loading from a link

Paste a GitHub link into the box on the drop screen and Benchdrop downloads
and opens it — `https://github.com/owner/repo`, or a specific branch with
`.../tree/branch-name`. A direct link to a `.zip` works too. Private
repositories need to be downloaded by hand, since Benchdrop doesn't ask for
your credentials.

Downloaded archives are kept, so re-pulling the same repo later behaves like
any other zip: if the contents changed, it re-extracts.

## Recent projects

The drop screen lists the last dozen projects you opened — click one to open
it again. Anything whose file has since been moved or deleted is greyed out
and marked, rather than failing when you click it.

## Languages

Benchdrop recognises and runs:

| Project | Recognised by | Runs with |
|---|---|---|
| Node / npm | `package.json` | your `dev`/`start` scripts (several at once if needed) |
| Static site | any `.html` file | Benchdrop's own server |
| Markdown | `.md` | rendered as a page |
| Python | `.py`, `requirements.txt` | your chosen script, with optional pip install |
| PHP | `composer.json`, `artisan`, `.php` | Laravel dev server or PHP's built-in server |
| Go | `go.mod`, `main.go` | `go run .` |
| Rust | `Cargo.toml` | `cargo run` |
| Ruby | `Gemfile`, `config.ru`, `.rb` | Rails, Rack, or a plain script |
| .NET | `.csproj`, `.sln` | `dotnet run` |
| Java | `pom.xml`, `build.gradle`, `.jar` | Maven, Gradle, or `java -jar` |

Node.js is the one runtime Benchdrop will fetch for you. For the others it
checks what's installed and, if the language is missing, says so and links to
the download rather than failing with a confusing error. Installing a language
toolchain silently isn't something a test tool should do behind your back.

A project that has both a runtime and a web page offers both, so you can open
the page directly without starting the server.

## Testing on a phone

The **Phone** button serves the running project over HTTPS on your local
network and shows a QR code to scan. Both halves matter:

* **On the network**, so the phone can reach it at all — Benchdrop normally
  serves only on localhost.
* **Over HTTPS**, because geolocation, camera and service workers only work in
  a secure context. `localhost` counts as one; a plain `http://192.168...`
  address does not. This is the difference between being able to test GPS on a
  real phone and not.

It proxies through to whatever is already running in the pane, so it works the
same for a static page, a Vite dev server or a Python app, and WebSocket
upgrades pass through so hot reload keeps working.

**What you do on the phone appears in the log too.** With Trace on, every
request the phone makes is logged as it passes through, and a small reporter
is added to the pages it loads so taps, typing, console output and errors come
back as well. Each line is tagged with the device it came from
(`[app · iPhone 192.168.86.42]`), so two phones — or a phone and this
computer — never get muddled. The reporter is injected on the way past and is
never written into your project. Passwords and anything that looks like a
secret are masked exactly as they are on the desktop side.

The certificate is generated by Benchdrop on your machine, so **the phone will
warn that the connection isn't private** the first time. Tap through the
warning; the connection is still encrypted and the page still counts as a
secure context. The certificate names your machine's current LAN address and
is regenerated automatically if that address changes.

## Right-click

Right-clicking works everywhere — the app being tested, the log, the command
bar and the URL box. Cut/copy/paste (with Paste greyed out when the clipboard
is empty), copy a link or image, search the web for selected text, reload, and
inspect element. Electron gives windows no context menu unless one is built,
so without this the only way to paste was Ctrl+V.

## Light and dark

**View > Appearance** switches between the dark workshop and a whitewashed
one. The choice is saved and restored next launch.

The light theme models a pickled (whitewashed) finish rather than simply
lightening the dark texture. Whitewash is semi-transparent: it settles *into*
the open grain, so the grain lines read lighter than the board — the reverse
of stained timber — and it's wiped back along the length, so it survives
unevenly, letting the wood's warm tannins through in streaks. Both textures
come from `build/make-wood.py`.

## Code view

The **Code** button in the toolbar switches the pane between the running app
and its source. A project always opens on the app; the toggle is only there
once something is running.

* Browse the project's files, filtered as you type. Dependency and build
  folders (`node_modules`, `dist`, `build`, `.git`, ...) are left out.
* Edit in place, with line numbers, syntax colouring and Tab indentation.
  **Ctrl+S** saves. A single-file app is coloured properly throughout — the
  CSS inside `<style>` and the JavaScript inside `<script>` are highlighted
  as CSS and JavaScript, not as markup.
* With live reload on, saving refreshes the page immediately — edit, save,
  see the result.
* **Export…** writes the whole project, including your edits, to a zip.

Highlighting covers HTML, CSS, JavaScript, JSX, TypeScript, JSON, Python,
PHP, Go, Rust, Ruby, Java, C#, YAML, Markdown and shell. It's done by Prism,
bundled with the app, so nothing is fetched from the internet. Very large
files are shown uncoloured rather than made slow to type in.

Files are read and written strictly inside the project folder; a path that
tries to climb out of it is refused. Binary files are detected and not opened
for editing.

## The log

Every line is timestamped. Output arrives in chunks that can split mid-line,
so the stamp is added when a line actually begins — a wrapped or split line
never gets one stuck in the middle of it. **Copy log** includes the stamps.

## Windows programs (.exe)

Drop a `.exe`, or a folder or zip with one in it, and Benchdrop runs it like any
other project. A dropped `.exe` runs from where it sits, so the DLLs and files
beside it are found; in a folder, programs at the top level are offered first,
then build output (`bin\Release` before `bin\Debug`), and uninstallers and
redistributables are ignored.

A native program can't be drawn inside a web view, so each feature has a
native equivalent:

| Feature | For a Windows program |
|---|---|
| **Pane** | a live picture of its window — or **Dock here** puts the real window inside the pane |
| **Log** | its console output, tagged with its name |
| **Stop** | ends it and everything it started |
| **Crashes** | the exit code decoded (access violation, stack overflow, unhandled .NET exception, DLL not found…) plus the faulting module from Windows' event log |
| **Trace** | windows opening and closing, title changes, *not responding*, child processes, focus moving between controls, files written in its folder and its AppData folder, and network traffic |
| **Capture** | its window at its real size, or a region of it |
| **Autotest** | drives it through Windows UI Automation — the accessibility layer screen readers use — pressing buttons, filling fields, opening dialogs, and catching crashes, hangs and error dialogs |
| **Live** | restarts it when the `.exe` is rebuilt |
| **Code** | the folder's files, as for any project |

**Network traffic** goes through a small local proxy that Benchdrop hands the
program in `HTTP_PROXY`/`HTTPS_PROXY`. Plain HTTP is logged in full; HTTPS stays
encrypted end to end, so you see the host, size and timing but never the
contents. Programs that ignore those variables and use only the Windows proxy
settings won't show up.

**Autotest coverage depends on the program.** Standard Windows, WinForms and WPF
controls expose themselves well. Custom-drawn interfaces (games, some
cross-platform toolkits) expose little or nothing, and Autotest will say it
found no controls rather than pretend.

**The pane is a picture until you dock it.** Undocked, it shows a live video of
the program's window: clicking it brings the real window to the front rather
than clicking inside it, and you may see a second mouse pointer - the
program's own, captured in the picture. Use the program's own window, or
**Dock here** to work with it inside Benchdrop.

**Electron and other Chromium-based programs** (CORE, VS Code, Slack, Discord
and the like) only show their buttons and fields to UI Automation when
accessibility is switched on; otherwise Trace sees little more than their menu
bar and Autotest has nothing to press. Benchdrop starts them with Chromium's
`--force-renderer-accessibility` switch, plus `--enable-features=UiaProvider`,
which lets Benchdrop read the screen in well under a second instead of up to a
minute. It spots most of them by Chromium's
files beside the `.exe`; a single-file (portable) build gives itself away only
when its window opens, so the first run says so and **Restart** applies it -
from then on it's remembered (`chromiumPrograms` in settings.json). Trace
records clicks as focus moving to the control that was clicked, so clicking
the same button twice in a row shows once. Anything the app makes clickable
without making it a real control (a plain clickable `<div>` rather than a
button or link) isn't visible to UI Automation, so Autotest can't press it.

**Docking** strips the program's real window of its frame and lays it exactly
over the pane, owned by Benchdrop so it stays on top of it, moves with it and
minimises with it. Some programs dislike having their frame changed; **Undock**
puts it back as it was, and the mirror is the safe default. While docked,
Benchdrop's own menus and panels hide the window while they're open, since it
would otherwise sit on top of them.

Windows locks a running `.exe`, so most builds need **Stop** first; **Restart**
runs it again.

If something doesn't work on a particular machine, **Help → Check native program
support** tests each Windows-specific part and says which one failed.

## Autotest

The **Autotest** button lets Benchdrop test the running app the way a person
would: clicking every control it can reach, filling in forms, following the
app's own navigation — and logging anything that breaks. At the end it writes a
report with the steps that led to each problem and a screenshot of it.

It tries every reachable control, fields before buttons so forms get submitted
with data. What it reports are the problems the harness sees directly — console
errors, uncaught exceptions, failed requests (4xx/5xx and network failures),
crashes, hangs — so they're reliable. To test toward a goal, or have each screen
judged as well, ask Claude through the [Claude connector](#claude-connector).

**Safety.** Anything that looks destructive or irreversible — delete, remove,
reset, log out, pay, buy, send, transfer, revoke — is skipped unless you tick
*Allow risky actions*, and the report lists what was skipped. What counts is the
action: a label that *starts* with one of those words ("Pay now", "Delete all
records") or a phrase like "place order" — not a word that merely describes
something, so "Jobs & pay rules" is opened like any other page. Links that leave
the app are never followed, and password or secret-looking fields are never
typed into. These rules are enforced in code.

Reports are saved to `%APPDATA%\benchdrop\reports\`.

Clicks are dispatched as DOM events rather than real OS input. That works for
virtually every web app; the rare exception is something that insists on
trusted events, such as file drag-and-drop.

## Claude connector

Claude can use Benchdrop directly, from a conversation in **Claude Desktop** or
**Claude Code**, with your own Claude account and no API key. **Help → Connect to
Claude…** sets it up. For Claude Desktop it shows the extension file,
`benchdrop.mcpb`, to drag onto Claude Desktop's **Settings → Extensions** page
(the Microsoft Store build of Claude Desktop doesn't open `.mcpb` files
directly). For Claude Code it shows a one-line `claude mcp add` command with
this install's paths filled in. A Claude Code connection does not appear on Claude
Desktop's Settings → Extensions page — that list is only for Claude Desktop. Check
it with `claude mcp list`, or ask Claude in Claude Code what Benchdrop tools it has.

Then ask Claude things like "open my project in Benchdrop, run it and check the
checkout flow" or "run an autotest on it and fix what it finds". Claude can:

| Tool | What it does |
|---|---|
| `benchdrop_open` | Open a zip, folder, file, program or link, like dropping it |
| `benchdrop_run` | Run it, with the same choices the picker offers |
| `benchdrop_status` | What's open and running |
| `benchdrop_snapshot` | The screen: text and every usable control, with ids |
| `benchdrop_act` | Click, type, change a selection, or go back / close a dialog |
| `benchdrop_screenshot` | A picture of the app or program |
| `benchdrop_log` | The log, including Trace |
| `benchdrop_autotest` | Run the explorer and get the report |
| `benchdrop_stop` | Stop everything |

Every action Claude takes is checked by Benchdrop, not just requested of Claude:
anything that looks destructive or irreversible is refused (Claude is told to
ask you instead), password and secret fields are never typed into, links out of
the app are never followed, and there is no tool for running commands. Each
action appears in the log marked `[claude]`, refusals included. After each
action Claude is told what Benchdrop detected — console errors, failed
requests, error dialogs, crashes.

How it works: Claude starts `mcp/benchdrop-mcp.js`, a small MCP server with no
dependencies, which passes each request to Benchdrop over a local connection on
127.0.0.1, protected by a random token in `%APPDATA%\benchdrop\connector.json`.
If Benchdrop isn't open it's started. Set `{"connector": false}` in
settings.json to turn the connection off.

## Trace

The **Trace** button makes the log show what the app being tested is doing,
not just what Benchdrop is doing:

* **clicks and typing** — which button, with its label; which field changed
  and to what
* **console output** — the app's own `console.log`/`warn`/`error`
* **network** — every request, its status, how long it took; failures marked
* **page events** — navigation, load failures, uncaught errors and unhandled
  promise rejections, crashes

Passwords and anything that looks like a secret (token, key, card, cvv, ssn,
otp, pin) are logged as `(hidden)` rather than their value, since a trace log
is meant to be copied and shared. Field values are never used as element
labels for the same reason.

Trace is **on by default** and sits with the log controls; the toggle remembers your choice. Combined with **Copy
log**, it turns "it doesn't work" into something specific.

## Live reload

Benchdrop watches the project folder and refreshes the page when a file
changes, so editing in your own editor shows up without clicking Reload.
Toggle it with the **⟳ Live** button; the setting is remembered.

`node_modules`, `.git`, `dist`, `build`, `__pycache__` and editor scratch
files are ignored, and a save that touches several files causes one refresh
rather than several.

For Node projects, Benchdrop does *not* force a reload — Vite and similar dev
servers push their own updates and usually preserve app state, so a forced
refresh would only throw that away. It notes the change in the log instead.

## Stable address

Benchdrop serves projects on **http://localhost:5599** when that port is free,
rather than a random port each run. That matters as soon as a project talks to
an API that allow-lists an origin or redirect URI. If 5599 is taken, Benchdrop
falls back to a random port and says so in the log. Override the port by
adding `{"port": 1234}` to `settings.json` in Benchdrop's app-data folder, or
turn the behaviour off with `{"fixedPort": false}`.

## Links to other sites

A link that points outside the project (`target="_blank"`, or a navigation to
another origin) opens in your normal browser instead of hijacking the app
pane or spawning a bare popup window.

## Using it (once installed)

1. Open **Benchdrop**.
2. Drag a project `.zip` onto the window, or click **Choose a .zip file**.
3. If it's a Node project, pick which script to run (Benchdrop suggests `dev`
   first, then `start`/`serve`/`preview` if present) and click **Run it**.
4. Watch the log panel while it runs `npm install` and then your script.
   Once it detects a `localhost` URL in the output, the app loads right
   into the window.
5. Use **Stop**, **Reload**, **↗ open in browser**, or **{ } devtools** from
   the top bar. **Load another .zip** resets Benchdrop for the next project.

Static sites (a folder with just `index.html`/CSS/JS, no `package.json`) are
also supported — Benchdrop serves them directly, no install step.

### What Benchdrop can't do for you
It runs `npm install` and your scripts. If a project needs its own account or
API keys, you sign in yourself — Benchdrop surfaces the link and keeps the
result, but never handles your credentials.

## Installing it

Download `Benchdrop_v4.3.3_win-x64_setup.exe` from the [releases page](https://github.com/Griffith-Software/Benchdrop/releases).

Run `Benchdrop_v4.3.3_win-x64_setup.exe` and follow the installer. It installs
for you only, in `%LOCALAPPDATA%\Programs\Benchdrop`, with no administrator
prompt. It shows the license, adds a Start menu shortcut, and offers a desktop
shortcut on its last page (unticked). If Benchdrop is running, the installer
closes it first.

Silent install and uninstall (exit code 0 when they succeed):

    Benchdrop_v4.3.3_win-x64_setup.exe /S
    "%LOCALAPPDATA%\Programs\Benchdrop\Uninstall Benchdrop.exe" /currentuser /S

Uninstalling from Settings → Installed apps asks whether to also delete
Benchdrop's data (`%APPDATA%\benchdrop`: unpacked projects, settings,
screenshots and the downloaded Node.js); the answer defaults to keep. A silent
uninstall always keeps it.

To check a download, compare its SHA-256 with the published value:

    Get-FileHash .\Benchdrop_v4.3.3_win-x64_setup.exe -Algorithm SHA256

Windows may show "Windows protected your PC" when you first run a new release,
because Windows has not yet seen enough downloads of it. Check that the SHA-256
shown here matches your file, then choose More info, then Run anyway. This
release is not code-signed.

Benchdrop has no update check. To update, run the next release's installer;
it upgrades in place and keeps your data.

## Projects that need their own backend

Some projects have a backend service that must run alongside the app (and
sign you in the first time). Benchdrop handles this:

* **Run several scripts at once.** The script picker is multi-select. Benchdrop
  pre-ticks what it thinks "running this project" means — any backend-looking
  script (`dev:convex`, `dev:server`, ...) plus one frontend script.
* **Sign-in links are surfaced.** If a script prints a sign-in URL, a banner
  offers to open it in your real browser. Every URL in the log is clickable
  too. You authorize with your own account; Benchdrop never handles credentials.
* **Answer prompts in-app.** The box under the log sends a line to a running
  process's stdin, so CLIs that ask questions can be answered without leaving
  Benchdrop. This is a pipe, not a real terminal (no PTY) — a CLI that demands
  a TTY may still refuse to prompt. If you hit that, use **Folder** to open
  the project on disk and run the command in a normal terminal once; the
  result is kept (see below).
* **Run any command.** The bar at the top of the log runs a command in the
  project folder — the escape hatch for setup steps that aren't in any npm
  script (`npx @convex-dev/auth`, `npx prisma migrate dev`, and so on).
* **Any HTML file counts as a UI.** The web entry point doesn't have to be
  named `index.html` — Benchdrop finds any `.html` file near the top of the
  project, ranks the likely candidates, and serves the best one.
* **Projects with both.** If a folder has a web page *and* Python scripts,
  Benchdrop asks which you want rather than guessing — useful for a CLI tool
  that also ships a standalone browser version.
* **Python projects.** Benchdrop detects Python projects and works out whether
  they serve a web UI (Flask, FastAPI, Django, Streamlit, Gradio, etc.) or are
  command-line only. Web ones load in the pane; CLI ones say so plainly and
  stream their output to the log. It can also pip-install from
  `requirements.txt` first. Note: Benchdrop downloads Node.js when a project needs it, but **not** Python —
  if Python 3.9+ isn't installed, it says so instead of failing cryptically.
* **Says what it found, not just what's missing.** A folder with no runnable
  web app no longer errors out. Benchdrop reports that no UI was detected,
  lists what the folder actually contains, and opens in command-only mode so
  the command bar still works against it.
* **Copy log.** A toolbar above the log copies the whole thing to the
  clipboard as plain text (URLs and `[script]` prefixes intact, no markup),
  with a Clear button beside it.
* **Capture feedback.** A camera-shutter flash over the app pane and a short
  confirmation card with a thumbnail, so it's obvious a shot was taken (and
  of what) without reading the log.
* **Screenshots.** The Capture button offers three modes: the visible area,
  the **whole page including everything you'd have to scroll to see**, or a
  region you drag a box around. Shots are saved to Benchdrop's screenshots
  folder (openable from the same menu) and copied to the clipboard so they
  can be pasted straight into a message. Full-page capture drives the Chrome
  scrolling a screenful at a time and stitching the results, because a
  <webview>'s compositor surface is pinned to its on-screen size — asking
  Chrome to capture beyond it just repeats the viewport. Anything pinned to
  the window is handled so it doesn't repeat: a sticky header is kept for the
  first screenful and hidden after, and a bar pinned to the bottom of the
  window is hidden from the start, since it would otherwise be stamped across
  the middle of the finished image.
* **Clear cache.** Next to Reload — clears the app view's browser cache,
  cookies, local storage, and service workers, then forces a real reload.
  Separate from Reset project / Clean reinstall: this never touches files on
  disk, so it's the right tool when a dev server is serving fine but the
  embedded browser is showing something stale (old bundled JS, a stuck
  service worker, cached login state).
* **Status indicator.** The pill next to the Benchdrop title shows what's
  happening at a glance: a spinning icon while something is actively running
  (installing, starting, a setup command), a green dot once the app is up, an
  amber spinner if a step is taking unusually long, and gray/red for
  stopped/error. Buttons that would start a duplicate action are disabled
  while something is already running.
* **Picks the right URL.** When a backend script (Convex, etc.) is running
  alongside the app, Benchdrop ignores that backend's own local address (e.g.
  Convex's http://127.0.0.1:3210) and waits for the actual frontend script's
  URL, so the app loads instead of a bare backend endpoint.
* **Fix suggestions.** Benchdrop watches output for known "you skipped a setup
  step" errors and offers the command that fixes it. It never runs one on its
  own — these change your own cloud resources, so you press the button.
* **Stuck ports.** If a script can't start because a leftover server from a
  previous run still holds its port, Benchdrop spots it, identifies the process,
  and offers to stop it and retry.
* **Updated zips are detected.** The folder is keyed to the zip's path, but
  re-use is decided by its *contents*. Drop in a rebuilt zip with the same
  filename and Benchdrop unpacks the new code over the old — it won't silently
  serve what it unpacked last time. Installed packages and local settings
  (`node_modules`, `.env.local`, generated backend code) are kept.
* **Setup persists.** Each zip gets a stable folder keyed to its path, so
  `node_modules`, `.env.local`, and any generated backend code survive the
  next run. **Reset project** wipes it and starts clean.

## Rebuilding it yourself

This repo is a normal Electron app.

```bash
npm install
npm start          # run it directly, unpackaged
npm run dist        # build release/*.exe (Windows installer)
```

Building the Windows installer works natively on Windows, and also works on
Linux/macOS **if wine is installed** (electron-builder uses it to build the
NSIS installer). The included GitHub Actions workflow
(`.github/workflows/build-windows.yml`) builds it for you on a real Windows
runner with zero local setup — just push this repo to GitHub and run the
workflow (Actions tab → "Build Windows installer" → **Run workflow**), then
download the installer from the run's Artifacts.

### Customizing
- **App name**: edit `name` and `productName` in `package.json`. Leave
  `appId` alone: the installer's identity comes from it, and changing it stops
  new versions upgrading old installs.
- **Icon**: `build/icon.ico` is the app/installer icon (already wired up for
  the exe, installer, and uninstaller). `npm run build:icon` regenerates it,
  `build/icon.png` (1024 px) and the square master `build/icon-master-1024.png`
  from the shapes and colours in `build/make-icon.js`; it runs in Electron, so
  nothing else is needed.
- **Behavior**: `main.js` has the unzip/detect/install/run logic; `renderer/`
  has the UI.

## How the runtime works

Benchdrop needs a real Node.js to run `npm install` and your dev script. On
first run it resolves one in this order:

1. A Node runtime Benchdrop downloaded previously (kept in its app-data folder).
2. A Node.js already installed on your machine, if it's 20.19 or newer.
3. Otherwise it downloads the current official Node.js LTS from nodejs.org
   once (~30 MB) and reuses it from then on.

That resolved Node is also put at the front of `PATH` for everything Benchdrop
spawns, so packages whose install scripts shell out to a bare `node`
(esbuild and friends) resolve to the same working runtime.

> Earlier versions tried to reuse Electron's own embedded Node instead, to
> avoid any download. That works for direct invocation but breaks for
> packages that shell out through `cmd.exe`, which fail with errors like
> `[ERROR:icu_util.cc(223)] Invalid file descriptor to ICU data received.`
> Using a real Node executable avoids that class of problem entirely.

## Known limitations

- A project's servers are ended when you press Stop, load another project or
  close Benchdrop. If Benchdrop is ended any other way (Task Manager, a crash),
  Windows leaves them running and holding their ports; the next time Benchdrop
  starts it ends whatever was left of that session and says so in the log.
  When a server finds its usual port taken and moves to another one (Vite
  does), Benchdrop says which process holds the port and offers to free it.
- Each zip you drop in is unpacked to a folder under Benchdrop's app-data
  directory, reused when the same zip is dropped again (so `node_modules` is
  kept) and re-extracted only when its contents changed.
- Dev-server URL detection is done by pattern-matching the process output for
  something like `http://localhost:PORT`. Most tools (Vite, CRA, Next, etc.)
  print this, but an unusual one might not — the log panel will still show
  you what's happening.
- Native modules that need to compile from source (rare in typical
  React/Vite-style front-end projects) may fail without a real Node/npm
  install and build toolchain — Benchdrop only covers the common case.

## About the name

This app was called DevBox Emulator until v2.0.0. It was renamed because
"Devbox" is already a well-known open-source dev-environment CLI (Jetify) and
"Dev Box" is a Microsoft Azure service — both in the same category, which would
have made the tool hard to find and easy to confuse.

On first run, Benchdrop copies your projects, settings and screenshots over
from the old DevBox app-data folder, so nothing you'd already set up is lost.
The old folder is left in place as a fallback and can be deleted once you're
happy everything came across:

    %APPDATA%\devbox-emulator
